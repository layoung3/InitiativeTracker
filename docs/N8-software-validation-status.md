# N8 software validation and remaining acceptance

PR #4 remains an opt-in, unmerged prototype. Neither working Raspberry Pi has been accessed, configured, installed, rebooted or tested. The owner has no spare Pis, cards or other Pi storage. No hardware purchase is required to continue software work. Final commit and exact-head CI links are recorded in PR #4; this document is versioned with its source.

## Defects corrected during software closure

- Finish-pairing previously accepted an expired candidate, including expiry during awaited approval/recovery requests. The agent and root broker now recheck the original authorization deadline, intent and generation. A phone candidate cannot outlive its original AP lease.
- Root rebind and agent binding-save were separate writes without a durable reconciliation intent. A crash/lost reply could leave mismatched generations. The agent now persists authenticated pending binding before root mutation, and root saves an exact committed receipt atomically with its new generation. Restart completes that approved commit without the hub; an expired uncommitted intent cannot replace trust.
- Owner forget and deletion of old owned NM profiles could be interrupted. Forget now has durable precedence over pending pairing. Deferred root cleanup checks actual UUID existence, persists progress, retains adopted preferred/recovery profiles and safely retries an already completed deletion. Armed recovery is retained until its fixed deadline; explicit owner reset after expiry does not depend on reaching the old hub.

Regression fixtures cover these cases, A→B→A requiring fresh approval, and old-generation rejection. No additional implementation defect is currently identified by these checks; this is not a claim of exhaustive correctness or physical acceptance.

## Outstanding physical cases, optional later

1. **Actual Wi-Fi and independent rollback:** saved WLAN A→B, WLAN↔hub AP, failed join and confirmation expiry with web/agent stopped. Measure real activation/scan/controller timing, driver/regulatory behavior, AP DHCP, mDNS/pinned fallback routing and real NM failure responses. Confirm each radio returns independently and no indefinite cycling occurs.
2. **Outage and boot recovery:** brief interruptions preserve the network; confirmed two-minute outage triggers bounded attempts; correct hub return restores service after multiple cycles. Verify finalized-profile activation after real boot and armed-plan recovery after restart. Controlled abrupt power interruption is separately optional/risky; process fault injection already covers logical write seams.
3. **Kiosk/pairing/peripherals:** actual Chromium/Labwc process and retained profile/cookies recover after radio outage and boot; original display pairing and encounter updates persist. Check real touchscreen/local Setup action and keyboard usability. No dedicated button or physical keyboard is required for ordinary recovery.

Phone AP/client DNS, Android/iOS certificate/browser behavior and headless owner-bundle usability remain a separate acceptance phase. Their authorization/state logic is already software-tested; successful fake-NM HTTPS routes do not prove an ordinary customer phone can resolve or trust an offline setup hostname.

## Dependencies and optional restoration procedure

The current two production cards remain untouched. Later, only if approved: obtain two disposable microSD cards, a reader and private image space; use the existing two Pis/power/displays and an isolated router offering two synthetic WLANs. Arrange a recovery console, valid clocks and a recovery operator. Additional Pis are optional, not required. Reassignment can use a second distinct synthetic hub snapshot sequentially rather than a third Pi. Do not clone production identities, cookies, keys, credentials or data into the lab.

Follow [the gated installation and rollback sequence](N8-authentication-and-core-hardware-trial.md). Inventory boot media first; separate cards do not isolate USB/NVMe, EEPROM/firmware or peripheral state. Approve safe isolation without firmware/boot-order changes. Shut down and confirm power-off; label/store original cards. Image/install only the disposable cards. Use exact reviewed source/artifact hashes, matching agent/broker and full paired snapshots. After the trial, power off, remove lab cards, restore original labelled cards/approved original boot-media arrangement and verify unchanged 0.1.5, pairing, encounter and kiosk. No binary-only downgrade or production filesystem mount from the lab OS. If persistent hardware/firmware state differs, stop: swapping cards cannot restore it. The cost of this option is downtime and card/connector/boot-selection risk; spare devices avoid production downtime but cost more and may not match peripherals.

Core pinned-agent mTLS needs no purchased domain. Fresh N8 DM login additionally needs validated browser HTTPS: a synthetic CA explicitly trusted only in disposable lab server/browser stores can satisfy it with an exact localhost SAN. Trust installation and certificate creation on those future cards require approval; no customer CA installation or warning bypass is prescribed. Use saved synthetic WPA profiles initially; never enter PINs/Wi-Fi/owner secrets over HTTP.

## Remaining implementation/infrastructure limitations

There is no identified blocker to the documented **manual, opt-in core lab trial** once storage, lab trust and installation approval exist. This is not production-ready commissioning. Complete N8 agent installation is still manual; the original satellite installer alone is insufficient. Automated public certificate issuance/renewal/distribution, product-domain selection and per-device offline phone DNS configuration are not implemented/configured. They remain separate production infrastructure work, not physical-radio tests. Existing nullable/stack-allocation warnings are outside these N8 changes. No domain purchase, certificate issuance, real-device installation, merge or deployment is authorized by this report.
