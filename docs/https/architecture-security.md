# Shared trusted HTTPS checkpoint

This is an independent master-based checkpoint, disabled by default. It does not merge N8 or N9, install anything, run a production migration, change a Pi, or issue a certificate. Base: `d584b7963ca6bb7916f21d9ee94082f9f2821f34`. Reviewed source contracts: N8 `93e93d37ffa5dfdc809434751f6b641087d7913c`, N9 `1e86dc520f9aa5e228b5639f1e31e9f7f19e0caa`.

## Architecture and implementation

One dedicated, owner-selected public DNS hostname identifies one hub. A maintained ACME client and reviewed DNS provider plugin prove control with DNS-01. Their private state and scoped credentials belong to a separate issuer process; the web app can read only its leaf certificate/key bundle. Issuance uses outbound connections, without port forwarding, public listeners or public A/AAAA records. DNS-01 challenge records and private gameplay name resolution have different purposes.

`https-infra/foundation.py` implements bounded certificate validation, dry-run, renewal adapter invocation, serialized activation, immutable generations, atomic manifest replacement, served TLS acknowledgement, rollback and DNS preflight/template generation. `certbot_adapter.py` implements the actual Certbot `certonly`/DNS-01 initial issuance, recorded-policy renewal, scoped provider configuration, version gates, bounded propagation settings, safe archive-link resolution and validated immutable 0600 exports. It delegates ACME, DNS API operations and challenge cleanup to the maintained Certbot/plugin implementation, rather than implementing those protocols or cryptography. No backend is installed or invoked against real services in this checkpoint. It uses Python's standard library and the distribution OpenSSL executable. Existing .NET TLS/X509 libraries perform application-side validation independently. No new NuGet/Python package is added.

`BrowserTls:Enabled` adds direct Kestrel TLS on 5445, while retaining configured HTTP endpoints. No reverse proxy or forwarded-header authority is involved. Unknown SNI names fail the TLS handshake. TLS requests also require the configured Host/port and a real TLS feature; sensitive operations cannot use an alternative origin. The newly configured public hostname rejects HTTP entirely, including login forms, without redirecting; legacy IP/`.local` gameplay origins retain their migration behavior. The new listener binds on local interfaces, so its eventual deployment also needs reviewed local firewall rules: no WAN ingress, router forwarding, UPnP or cloud tunnel. It is not made internet-facing by this checkpoint.

The issuer validates a complete chain using installed public roots, server purpose, dates, a single exact DNS SAN, matching private key and at least 24 hours remaining before promotion. No wildcard, CN fallback, private CA option or disabled TLS validation exists in production configuration. A PFX bundle is written to a generated directory, then an `active.json` manifest is atomically replaced. Both processes restrict path types, links, permissions and input sizes. The app accepts only generated identifiers, never paths supplied in requests. The store is outside releases and outside the web root.

Kestrel polls the manifest every two seconds. Valid replacement certificates are used for new TLS handshakes without restarting the app, desktop, updater or sockets. The issuer independently connects to loopback using the configured hostname as SNI and normal certificate validation, compares the peer leaf's SHA-256 fingerprint with the expected candidate/rollback leaf, then checks the app's generation acknowledgement. The fingerprint binds acknowledgement to the actual TLS handshake, so an old TLS connection cannot falsely acknowledge a newly reported generation. That avoids depending on LAN DNS for local activation while still validating the hostname. Successful no-issuance renewal runs confirm the existing served generation without copying keys or consuming reload history. Failed issuance leaves the manifest alone; failed activation restores the prior manifest and verifies the old serving generation. Unconfirmed recovery is reported as a failure. A failed first activation, with no previous generation, publishes an explicit disable request and reports recovery unconfirmed; the app clears its active TLS state when it reads that request. The app retains its last valid in-memory generation if files are corrupt or unavailable and rechecks trust/dates for each new handshake and sensitive request. An expired generation is never a usable HTTP fallback.

A four-generation strong-reference cache supports quick rollback without a lifetime rotation cap. Each selected `SslStreamCertificateContext` holds its certificate references for the stream using it. Eviction drops only the cache reference: it never calls Dispose on an in-use context. Retired certificate SafeHandles finalize after all stream/context references disappear. App shutdown disposes the remaining cached material after server shutdown. The published-app test rotates beyond the former 16-generation limit; no automatic app restart is introduced. Archived keys require controlled retention and protected backups; there is deliberately no automatic deletion of material that may be in use. `/system/https-status` exposes only readiness, generation ID and leaf expiry, never credentials or paths; readiness is true only on the trusted TLS origin. Monitor the served TLS connection and its actual expiry, with alerts appropriate to the certificate's issued lifetime. No assumed fixed certificate lifetime.

## Threat model and security review

Protect browser credentials/private media against LAN interception, malicious DNS/Host headers, accidental HTTP submission, malformed certificate inputs, stale addresses and credential/key disclosure through releases/logging. Trust the OS public-root store, privileged issuer/operator, installation ownership, the hub application process and physical administration. Compromise of root or the web process's memory is outside this boundary; the app necessarily holds its serving private key. Do not use the browser key as an agent identity.

| Boundary | Control and remaining limit |
|---|---|
| DNS API credentials | Separate root-owned issuer state, 0600 credential file, no token in argv, environment or web app. Choose record scope if supported, otherwise a delegated challenge-only zone. Zone scope is broader than record scope. No provider request is made here. |
| Private leaf key | Per-hub, generated by maintained backend, restricted PFX permissions, root-owned store and read-only app group. Unencrypted PFX relies on OS permissions; encrypt backup volumes/media. No shared fleet wildcard key. |
| External commands | Fixed OpenSSL executable and reviewed private renewal adapter; no shell interpolation. Bounded inputs/timeouts and captured stdout (256 KiB, 4 KiB for backend version); stderr and unused renewal output go to the null device, with static error messages and sanitized environment. Ambient Certbot default config files are rejected rather than assumed overridden by `--config`. Child process groups are cleaned before the leader is reaped, including TERM-resistant descendants. Adapter/backend must also redact provider logs; issuer logs stay private. |
| Host/rebinding | Exact SAN, SNI, HTTP Host and actual local port; no forwarded headers. Rebinding can redirect traffic but cannot create a trusted certificate or authenticated session. Existing antiforgery, ownership and DM checks remain mandatory. |
| Offline trust | Chain downloads disabled; uses installed intermediate/root material. Revocation is deliberately not an online runtime dependency. Offline clients cannot reliably learn revocation; browsers apply their own policies. Root-store updates still need planned maintenance. |
| Private address resolution | Only explicitly selected assigned RFC1918/ULA addresses, no wildcard addresses, loopback, link-local, public DNS writes or auto-selected first interface. Reject stale A/AAAA mixtures. Tool never changes DHCP/DNS. |
| Failed renewal/reload | Valid last-known-good remains available. Incorrect/expired/future/untrusted certificates fail closed. Rollback revalidates current trust and dates. Persistent file failures may need physical maintenance. |
| Application sessions | HTTP gameplay stays at its existing origin. A separate browser-bound Secure/HttpOnly/Strict cookie requires fresh physical DM proof or explicit secure-DM approval of an exact player/display request. Legacy credentials propose identity only. Persistent generations revoke changed identities; media grants cannot authorize N8 network or agent operations. See the secure authorization guide for expiry, recovery, storage-failure and backup limits. |

There are no new application/database schema migrations in this checkpoint. Existing master still calls `Database.Migrate()` at startup, so **starting a new app binary on the production database remains a separately approved deployment/migration action**, even when no new migration file was added.

## Secure authorization and independent integration evidence

The owner-approved [secure authorization implementation](secure-feature-auth-scope.md) adds physical-screen DM proof and DM-approved player/display enrollment without upgrading legacy HTTP credentials. Proof is displayed only at the configured trusted HTTPS origin with both connection addresses loopback. This requires a separately approved hub-only DNS override; no code appears on the old HTTP Setup page. Immutable identity snapshots, persistent revocation generations, exact pending-browser binding, CSRF, bounded requests and fixed session expiry protect private-feature authority. Ordinary gameplay remains available; identity/security/visibility and character-configuration mutations require fresh secure authority when the optional foundation is enabled.

N9 mutations are at `/appearance` and private GETs at `/media`. The transport guard rejects sensitive HTTP before model binding, then the secure authorization policy requires a fresh grant alongside N9's original ownership, DM, antiforgery, decoder and storage checks. The actual frozen N9 source is archived into a disposable integration fixture with the candidate modules and deterministic Program wiring. Its real branding writes, PNG uploads, private reads, cross-owner denial, display visibility and recovery handlers run in tests. Asset-owner provenance also prevents legacy character reassociation from transferring private artwork. No N8/N9 branch is merged or modified.

This fixture is meaningful software integration evidence, not a combined production release. A later reviewed N9 patch must wire the modules and align its transport-only UI guidance with shared readiness/hostname/port policy, preserve generic default portraits and configurable branding, and repeat the complete combined suite. N9's presentation schema and physical deployment remain separately gated. Actual N8 provisioning is not exercised by the fixture; all reserved agent/network routes reject media authority here.

N8's `DmAuthenticationPolicy` checks actual Kestrel TLS, local BrowserTls port and matching Host port, and uses a separately authenticated SecureDm cookie. Its current `PublicCertificateHttps` loads a PFX once. A later integration patch must implement its `IProvisioningHttps` over this shared live certificate source and remove its duplicate browser listener/file loader. Keep the secure DM scheme, physical approval, session claims, network authority, size/rate limits and pinned-agent enrollment unchanged. The pinned agent listener on 5443 and its coordination key/trust files must never point at this store. Browser renewal must not re-enroll agents or rotate their pins. Reserved credential provisioning and coordination routes fail closed here even for a secure media DM; the actual N8 independent agent identity, explicit approval and network-authority policies are still required.

## Practical setup and future customer devices

For one private hub: owner domain/subdomain, one public leaf certificate, direct TLS on 5445, a maintained DNS plugin and narrow credential or delegated `_acme-challenge` zone. Prefer hub-hotspot operation for venues without a cooperative router. On a managed home LAN, use router/resolver local overrides plus stable DHCP reservations and verified client resolution. Keep existing display-only satellites on their current gameplay origin until individually approved; they do not need server certificates just to display the hub.

For customers: provision an independent hostname, leaf key, issuance scope and lifecycle per device. Define who owns the domain, ACME account/terms, DNS provider, renewals, revocation and support on transfer/end of service. A central challenge service is possible later, but must authorize each device only for its own challenge record; do not ship a shared DNS token or wildcard private key. Device-agent physical pinning remains a separate identity system. Disconnected devices cannot renew forever: publish expiry status and require periodic connectivity or controlled certificate delivery.

## Primary sources reviewed

- [Let's Encrypt challenge types](https://letsencrypt.org/docs/challenge-types/): DNS-01 for private services, scoped credentials and challenge delegation.
- [Certbot renewal and deploy hooks](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates): maintained renewal policy; successful process exit does not by itself prove a new certificate was issued.
- [Kestrel endpoints and dynamic TLS callbacks](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0): direct dynamic certificate selection.
- [dnsmasq manual](https://dnsmasq.org/docs/dnsmasq-man.html): exact host records and local resolver behavior. NetworkManager's private dnsmasq instance must be configured through its supported integration, not a competing daemon.
