# Secure-feature authorization implementation

Implemented in the independent HTTPS branch following owner approval for source and automated testing only. N8/N9 are unchanged and unmerged. No certificate installation, real issuance, production migration, host networking or Pi changes are performed.

## Trust and enrollment

`SecureFeature` is a separate authentication scheme with a separate Data Protection purpose, secure ticket, browser binding, origin, game session, immutable identity snapshot, grant identifier and revocation generation. Ordinary `InitiativeTracker.Auth`, player-device/recovery bearers, display pairing and the old DM PIN cannot issue it. Existing gameplay remains authenticated through its original scheme; protected requests require both identities to match exactly. Mixed players, roles and display identities are rejected.

The hub's physical authorization screen is **`https://<configured-host>:5445/secure-access/physical`**. It requires actual trusted TLS and both local and remote loopback addresses, exact configured Host/port, no forwarding-header authority. A literal `localhost` URL cannot substitute for the certificate's DNS SAN. There is no HTTP proof endpoint, QR code or secret URL. The legacy Setup page adds only a non-secret link to this HTTPS screen; `/setup/dmqr` and the old PIN remain legacy credentials and never unlock secure features.

1. On the browser to authorize, open `/secure-access` through trusted HTTPS and request DM proof. First use or loss/corruption of approval state uses **Initialize or recover**. This explicitly revokes all previous secure approvals when completed.
2. On the physical screen, match the 128-bit browser reference and purpose. Read the 64-bit random one-time code there and type it into the requesting browser's HTTPS form. The code is bound to its full browser secret hash, origin, purpose and current game/DM identity snapshot; it expires after five minutes, allows five failures and is atomically consumed before persistence/sign-in.
3. Players/displays first identify themselves through the existing HTTPS join/pairing flow. That credential establishes only a proposed identity. Request enrollment at `/secure-access`; a securely authorized DM compares the exact browser reference and profile/display identity and explicitly approves it. The requesting browser must finish the same pending request with the same secret and identity. Players do not need physical hub access.
4. A display ticket remains read-only, subject to trusted-device checks and N9's current encounter projection. It does not expose profile-private media. A media/character DM ticket never grants network administration or satellite-agent enrollment. Those reserved routes fail closed until N8's independent pinned device identity, explicit agent approval and network authority are integrated.

All new authorization forms use Razor antiforgery validation and exact Origin checks; cookies are `__Host-`, Secure, HttpOnly, Path=/ and SameSite=Strict. No code is model-bound into redisplayed form values. Request/response logging is not enabled for bodies or cookie headers, and new diagnostics never include secrets. The requester sees only a public verification reference, never its proof. Physical requests/attempt budgets can be cleared only through a CSRF-protected trusted-loopback form. Loopback DM admission has priority within the bounded queue so the physical owner can recover when remote requests fill it.

## Durable state, expiration and revocation

Data Protection keys remain in the existing persistent data directory. Secure state is separately protected under `InitiativeTracker.SecureAccess.State.v1` in `<Tracker:DataDirectory>/secure-access/state.bin`, with a private 0700 directory and 0600 files, outside releases. The directory must be explicitly configured outside the web content root; no secure session is minted before persistence succeeds. No EF schema is added.

Tickets/grants have a fixed twelve-hour lifetime and no sliding renewal. Pending challenges and approvals expire after five minutes and are deliberately invalidated by an application restart. Durable approved sessions survive an ordinary restart with the same database, Data Protection keys and secure state. Missing, corrupt, unsupported or interrupted state fails closed; legacy credentials never initialize it. Fresh physical recovery creates a new epoch without changing gameplay identities or rotating Data Protection keys.

Each write first records a flushed mutation fence, then flushes a protected replacement and atomically replaces the state file. An interrupted/failed commit leaves the fence and blocks secure authorization across restart until physical recovery. The current process also fails closed on persistence errors. If storage cannot record even the intent, no mutation can be acknowledged; unchanged prior state cannot record a failed attempt across restart. Treat failed revocation as unconfirmed and require physical recovery after storage repair—never interpret a restart as successful revocation. Power-loss filesystem durability is not hardware-validated here.

Revocation generations are durable and never restored by routine ticket renewal. Player snapshots include stable profile/connection/credential identifiers, creation timestamps, credential hash and recovery-key hash. Display snapshots include the exact registered display and pairing generation; DM snapshots bind the game session and PIN generation. Missing/revoked/reassociated identities fail validation and are durably revoked once observed. Identity/security mutation handlers revoke affected grants and pending approvals before executing their changes; failure to persist blocks the mutation. A player can invalidate only their own profile, regardless of extra form/query IDs. Normal presence updates and cosmetic names do not invalidate approval.

The queues are bounded: 32 pending requests, 128 rate buckets, ten begins/redemptions per source per minute, five wrong proof attempts, and 256 retained grants. Expired entries are pruned. Cancellation revokes this browser's grants as well as pending requests, closing concurrent finish/cancel races. Approval revalidates the approving DM grant; revoking that approver prevents completion of still-pending enrollments.

## Indirect escalation and existing gameplay

Under enabled browser TLS, sensitive DM player/profile/device mutations, combat visibility/controller assignment/restore/undo and player configuration/edit/create/recovery operations require fresh secure authority. HP, initiative, turns, resource use, conditions and existing display/gameplay sessions retain their original flow. Existing pairing state is preserved; approving new pairings is sensitive administration. The migration guide must be followed before enabling this policy on hardware.

Actual `/DM/Players`, `/DM/Devices`, `/DM/Profiles`, remembered-profile/recovery and player sign-out/device-revocation paths are included in the tests/audit. Legacy destructive actions cannot create or transfer secure grants. Pre-mutation invalidation uses the affected profile/device scope; a client cannot revoke another profile by adding a bogus parameter. Recovery/replacement never follows a new device credential automatically. Restoring identity fields after revocation does not revive the old ticket.

For frozen N9, the shared guard verifies upload-time asset ownership against current character ownership, preserving uniform 404 denial instead of following a later reassociation. Existing N9 owner/DM checks, antiforgery, rate/byte/pixel limits, decoding, private storage and public projection remain in force. Public application logo/default assets remain intentionally public.

## Backups and limitations

Do not restore a stale secure-state backup as if its revocation history were current. Restoring all old state and keys can revive otherwise unexpired tickets; without a non-rollbackable external trust anchor this cannot be detected after a full rollback. The supported restore procedure retains/restores gameplay database and Data Protection keys as approved, discards secure approval state and requires fresh physical recovery before private use. This limitation is not a claim of backup-rollback resistance.

The singleton hub process owns the state file. Multi-process/shared-store authentication is unsupported. Actual physical screen, phone public trust, local DNS/clock, kiosk, systemd and Pi validation still need their approved hardware window. Frozen N8 remains separate; its browser certificate provider and physical network proof need a reviewed integration patch, while its pinned agent listener/trust remains independent.

## Evidence boundaries

`SecureAccessWebTests` exercises actual authorization page handlers, protected endpoints and legacy handlers with test-only peer/origin injection. Production has no configuration/header bypass. `published_tls_smoke.py` additionally exercises the published Kestrel app through real TLS, physical proof, rotation and restart using a process-only synthetic CA. It never installs trust or logs proof/token values.

`n9_secure_overlay.py` archives exact frozen N9 `1e86dc520f9aa5e228b5639f1e31e9f7f19e0caa` into disposable storage, overlays candidate modules and a deterministic Program harness, then runs the actual N9 tests and new authorization/media cases. It does not merge, cherry-pick or change that branch. The fixture verifies real branding writes, upload/read, ownership isolation, display visibility, recovery and immutable asset-owner checks. This is software integration evidence, not a combined production release or hardware/public-CA acceptance test.
