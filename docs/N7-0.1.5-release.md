## Behavior

* Boot fallback now starts discovery early, requires two successful separated
  scans and approximately 60 seconds uptime, and refreshes discovery at the
  fallback decision. Saved external profiles are identified by UUID, station mode,
  interface and autoconnect eligibility, ordered by autoconnect priority. Each
  candidate gets one bounded 15-second activation attempt per boot. A visible but
  unusable saved SSID no longer blocks fallback forever.
* The 60-second target is a minimum discovery window, not a hardware guarantee.
  Timer scheduling (10 seconds plus 1-second accuracy), NetworkManager readiness,
  scan completion and candidate association may extend it. Multiple eligible
  candidates can extend it by roughly one attempt/timer interval each. Scan/read
  errors, unavailable/activating devices, pending recovery or return transitions
  fail closed and defer fallback. No forced cancellation of NM association occurs.
* The fallback shares both controller locks and checks both journals. Any active
  connection (including another AP or manual recovery AP) settles the startup
  policy for the boot; later outages remain the independent recovery controller's
  responsibility. It never automatically abandons an AP after players join.
* The new pre-NetworkManager unit repairs **only** the staged recovery keyfile's
  autoconnect setting, preserving credentials and UUID. Existing staging already
  uses `autoconnect=false`; it deliberately refuses overwriting existing profiles.
  Unknown APs, alternative keyfile locations and other profile drift require
  diagnosis, not blanket mutation. The preparation unit is a separately approved
  installation; adding source alone does not change a deployed machine.
* DM initial visibility/HP visibility are part of the single add mutation. Existing
  visibility checkboxes autosave sequentially, show saved/error state, and retain
  conditional retry after failure; the submit button remains available without JavaScript. Antiforgery and DM authorization remain required. Player-controlled
  combatants retain the pre-existing public/HP visibility exception.
* Connected authenticated players can submit their own active characters during
  setup. Ownership, phase and duplicate checks are within the encounter lock;
  handler checks also validate the connection/credential relationship. Existing
  authentication rejects stale sessions/revoked credentials. DM setup restrictions
  are unchanged.
* Exhaustion is a single current-level badge in DM/player/display views, persisted
  in encounter JSON and undo snapshots and synchronized to linked characters.
  No database migration is introduced. Round/turn context sticks while scrolling.
* Setup uses four side-by-side connection cards and a network panel at 1280×800,
  retains loopback-only access and response privacy headers, and provides display
  pairing QR and launch controls. It collapses to two/one columns on smaller screens.
  Phone-readable QR and touch sizing still need physical Waveshare validation.

## App deployment and rollback (only after approval)

1. Record the reviewed PR commit and approved version. Build the ARM64 package with
   `scripts/Build-InitiativeTrackerRelease.ps1`, validate its manifest with
   `scripts/Test-InitiativeTrackerRelease.ps1`, and stage using
   `scripts/Stage-InitiativeTrackerRelease.ps1`. Verify hashes after transfer.
   These PowerShell packaging commands were not run here (PowerShell unavailable);
   the Linux x64 Release publish was verified separately.
2. Identify the installed unit, current release symlink, service user, data directory
   and production configuration from read-only diagnostics. Do not assume bootstrap
   defaults match the deployed installation. Retain the entire previous release.
3. In an approved maintenance window, stop only the app service; back up SQLite
   consistently (including any WAL/SHM), DataProtection keys, private data directory,
   application configuration, systemd overrides and current release target. Keep
   backups private and preserve owner/mode. Record migration IDs and checksums.
4. Extract into a **new** release directory. Preserve the site's production config
   and external data path. Atomically change the current release symlink, then
   start the existing app unit. Do not run `hub-bootstrap/install-hub-release.sh`
   as an upgrade script; it is first-install tooling and omits networking resources.
5. Check `/system/health`, version/commit evidence, migration state, local Setup,
   remote Setup denial, DM login, player reconnect, encounter state and real display
   updates. Check logs without copying secrets. No new migration is expected.
6. On failure, stop the app, restore the old release target and configuration, and
   restart. If data rollback is required, restore the consistent backup while
   stopped; this discards subsequent play and needs explicit owner agreement.
   Preserve the failed data for diagnosis. Never overwrite an in-use database.

## Networking deployment and rollback (separate approval)

The app package does not install the network components. Retain a separately hashed
copy of the approved `pi-network` sources and unit files. Keep existing independent
recovery controller, socket bridge, manual switching gates and emergency access.

Before changes, record enabled/active unit states and back up the installed libexec
scripts, all affected units/overrides, root-only gate files and the exact recovery
keyfile with its metadata. Never print or attach its contents. Verify that the
expected recovery profile is the intended AP; do not repair an arbitrary AP.

During an approved local maintenance window, stop the boot-fallback timer and wait
for its service to finish. Install with root ownership and mode 0755 only:
`initiativetracker-boot-fallback` and `initiativetracker-prepare-startup` under
`/usr/local/libexec/initiativetracker/`; ensure the unchanged discovery dependency
is present. Install the reviewed boot-fallback timer and preparation unit under
`/etc/systemd/system/` with mode 0644; reload systemd. Preserve existing fallback
service and gate configuration. Enable the preparation unit for the next approved
boot (`WantedBy=NetworkManager.service`); do not restart NetworkManager or run the
preparation script against an active device during play. Restart the fallback timer
only if it was previously enabled and its owner-approved gate remains enabled.
Do not silently opt a dry-run installation into live switching.

With keyboardless escape/recovery verified and a person present, perform an
explicitly approved reboot. Check saved-network success, missing network fallback,
visible unusable network fallback, late radio readiness, manual AP retention and
both pending-transition cases. Record actual boot timestamps. Confirm the private
QR, player/DM access and independent recovery still work. Investigate unexpected
AP autoconnect rather than modifying all profiles.

Rollback networking independently: stop the new timer, restore previous scripts,
units/overrides and enabled states, disable/remove the new preparation unit, and
reload systemd. Restore the exact backed-up recovery keyfile only in an approved
maintenance window and with NetworkManager safely stopped or on the next approved
boot; preserve private permissions. Restoring `autoconnect=true` also restores the
old startup risk. Do not remove credentials, disable recovery, or reset networking
as a generic rollback. Revalidate emergency access and the prior working behavior.

## Local UI feedback refinements

User-reported local checks (separate from automated results): initial DM hide-HP/
hide-public flags, subsequent checkbox updates, owned-character submission,
initiative setting, and character-sheet condition/exhaustion updates worked.
The follow-up removes the normal JavaScript save button in favor of a conditional
Retry save button after failure. The original server-rendered submit button stays
available when JavaScript is disabled. The latest requested display layout puts
exhaustion immediately after the character name, with other conditions underneath;
it does not combine exhaustion with the conditions row or move the HP column.

Three additional Chromium regression cases in `scripts/tests/n7-ui.test.cjs` pass:
no-JavaScript fallback and pending/failure/retry/success button states; desktop
1280px and mobile 390px badge ordering, shared name line, separate conditions,
unchanged HP column, exhaustion-only/conditions-only states and level updates.
These use synthetic HTML with the actual application JavaScript/CSS and mocked
SignalR/fetch, without a running app, database or live network actions. With Node,
Playwright and a browser installed, run:

```sh
node --test scripts/tests/n7-ui.test.cjs
# For a system Chromium instead of Playwright's installed browser:
```
