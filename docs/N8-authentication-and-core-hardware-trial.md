# N8 authentication migration and first hardware checkpoint

N8-enabled hubs reject DM PIN submission over HTTP, including loopback, before Razor model binding. Fresh trusted browser HTTPS login creates a separate secure DM session. Network administration additionally consumes a fresh physical network-control code. A legacy gameplay cookie cannot enter N8 administration, even on HTTPS or the physical loopback interface.

No working Pi has been accessed or changed. Installation, card swaps, test trust, credentials, radio changes, reboots and power interruptions require later approval. PR #4 stays unmerged. Do not treat this document as permission to execute.

## Compatibility and migration

| State | Fresh DM PIN submission | Existing gameplay/display behavior | N8 administration |
|---|---|---|---|
| N8 disabled, original settings | Legacy HTTP login remains compatible and explicitly labelled unencrypted | Original cookies, encounter operation and display pairing retained | No N8 coordination |
| N8 disabled, `DmAuthentication:RequireTrustedHttps=true` | Trusted browser HTTPS only; optional migration before coordination | Player/display HTTP URLs retained | No N8 coordination |
| N8 enabled | Trusted browser HTTPS only, including on the physical hub | Existing legacy gameplay sessions remain usable until original expiry; their DM cookies do not slide/renew. Player/display flows retained | Fresh secure DM cookie plus independent physical code, both presented on trusted browser HTTPS |
| Missing, expired, untrusted or wrong-host browser TLS | PIN form omitted and POST refused; no HTTP fallback | Already-established offline gameplay and independent root recovery remain separate | Fresh administration blocked |

Preserving fresh legacy HTTP PIN entry and claiming that all DM authentication is encrypted are incompatible. The migration deliberately changes **opt-in N8 authentication**, not the deployed 0.1.5 installation. Retain N8-disabled compatibility until the approved browser TLS/bootstrap is ready. Setting `RequireTrustedHttps=false` cannot disable the N8 requirement. There is no N8 loopback HTTP PIN exception.

The PIN is generated once and persisted by `GameSessionService`; the source has no PIN-change/reset API. This correction does not invent one, rewrite the database or rotate production identity. A PIN previously submitted on legacy HTTP may already be known; N8 therefore retains a separate random physical proof rather than treating that PIN or its old cookie as sufficient network authority.

The application does not globally redirect HTTP pages. Existing configured redirection is not enabled by this change. The new browser TLS configuration does not emit hostname-wide HSTS, which could upgrade legacy display/player URLs on another port to unavailable HTTPS.

## Session and transport boundaries

- `/dm/login` serves no PIN form when its transport is disallowed. HTTP POST is refused before form/antiforgery processing when N8 or the optional strict migration is enabled. Invalid PIN values are removed before rendering.
- Trusted HTTPS PIN login issues `__Host-InitiativeTracker.SecureDm`: Secure, HttpOnly, SameSite Strict, Path `/`, twelve-hour fixed lifetime without sliding. It uses a separate authentication scheme/data-protection purpose from `InitiativeTracker.Auth`.
- Existing `InitiativeTracker.Auth` player/display behavior is retained. Legacy DM sessions do not become secure sessions simply by visiting HTTPS. `/dm/network` requires the secure scheme when N8 is enabled.
- Unlocking network control requires a fresh five-minute physical code submitted over trusted HTTPS by the fresh secure DM session. Its separate fifteen-minute `__Host-InitiativeTracker.NetworkAdmin` grant is bound to process, login ID and game-session ID. Reauthentication needs another grant; retries cannot extend an existing grant. Five failed proofs lock the current code.
- Physical agent approval still requires the actual physical screen and the full satellite fingerprint. There is no N8 local-cookie authority shortcut.
- Browser trust requires HTTPS, a ready `IProvisioningHttps`, exact configured host (or physical localhost with matching SAN), the configured Host port and actual Kestrel browser-listener port. Forwarded headers and agent TLS do not establish browser trust. Reverse-proxy termination is not commissioned by this checkpoint.
- Physical Setup and QR pages require loopback with an allowed local Host, or validated browser HTTPS over loopback. Secure login/network links use the configured validated browser origin, not request Host or `TrackerUrlService`'s HTTP default. No ready origin means no login/network QR. Player/display invitation URLs are unchanged.
- Hub `5443` remains agent-only; browser pages there are rejected. Browser TLS defaults to `5445`; satellite phone TLS defaults to `5444`; satellite non-secret local setup remains `127.0.0.1:5081`.

Readiness checks certificate key, validity, exact SAN and server-auth chain in the **server OS default trust store**, with supplied intermediates and no certificate downloads. Browser trust is independently required. An explicitly trusted isolated lab CA can satisfy these checks without a purchased domain or source bypass. There is no public-root allowlist or lab toggle. Malformed/unreadable configured PKCS#12 fails startup; expiry/untrusted state never enables HTTP authentication. Offline chain policy does not perform online revocation checks.

## Hardware choices: existing Pis or additional hardware

| Choice | Minimum | Risks and limits | Rollback |
|---|---|---|---|
| Existing hub/satellite, separate disposable cards | Two spare microSD cards, reader and private image storage; existing displays/power; isolated two-WLAN router; approved physical recovery console | Production downtime; wrong-card/boot-device risk; connector/display wear, power/storage corruption and shared hardware state. Cards do not isolate EEPROM/firmware or attached production storage. Highest fidelity to actual peripherals | Power off, remove lab cards and reinstall original labelled production cards; restore only approved original images if needed; check unchanged 0.1.5 pairing/encounter/kiosk |
| Two additional Pis/cards | Two compatible Pis, cards, supplies and suitable displays/peripherals, plus router/recovery access | Additional cost; model/peripheral differences may still require later production-model checks. Working system stays available; strongest separation from its storage | Power off lab devices and restore/discard only lab images; production never participates |

**Existing-Pi card swaps are a proposed option, not approved work.** Before approval, inventory all boot media and boot order read-only. A microSD swap is insufficient if USB/NVMe production storage can boot or mount. Do not update EEPROM/firmware or change boot order; separately review safe powered-off isolation, or use spare hardware. Use an approved OS image whose commissioning will not update persistent firmware. Do not mount production filesystems from the lab OS.

Before any swap, record serials, card labels, expected root device, boot-media arrangement, display/touch model and power/peripheral connections. Shut down normally, verify power-off, label and store each original card separately. Approved full production-image backups contain secrets and must remain private/offline; never boot them as lab systems or copy production identities, browser profiles, credentials or databases into synthetic lab installations. No backups or swaps have been performed.

## Gates and installation sequence

1. **Review only:** choose hardware option, named serials/cards, outage window and recovery operator. Approve neither install nor testing implicitly.
2. **Commissioning approval:** approve imaging, packages and installer startup effects, synthetic WLANs/identities, lab TLS and local browser trust. If using existing Pis, separately approve card swaps and boot-media isolation. Snapshot fresh lab images before installing.
3. **Immutable build:** record the final reviewed PR head and build from that exact clean commit. Use the existing hub release build/manifest validation scripts; publish the satellite self-contained `linux-arm64`. Keep hashes of archives, manifest, publish files and installed helpers/units. The package may still say `0.1.5`; version alone is insufficient. Do not publish to release feeds or use the graphical updater.
4. **Fresh hub only:** inspect then run `scripts/install-hub.sh` with the approved artifact and actual desktop account. Secure local prompts receive synthetic credentials. Existing-install refusal is a stop condition, not a force/cleanup opportunity. The installer starts base services and creates lab identity/data. Preserve private receipt/backups in `/var/lib/initiativetracker-install/`.
5. Verify `/opt/initiativetracker/current`, `/var/lib/initiativetracker`, installed revised socket broker/Wi-Fi provisioner/controllers and `initiativetracker-device-coordination`. The network bridge socket and independent network-recovery/network-return timers must be active, with the existing root-only gates. Preserve their existing recovery authority.
6. **Browser TLS and N8 opt-in approval:** configure root-owned `/etc/systemd/system/initiativetracker.service.d/n8-lab.conf` with `Coordination__Enabled=true`, `BrowserTls__Host`, `BrowserTls__Certificate`, optional protected `BrowserTls__Password`, and `BrowserTls__Port` (5445). Protect the PKCS#12 root:app 0640 and its directory 0750. Reload/restart only the lab web service; validate normal browser HTTPS before any PIN entry.
7. For the smallest physical-hub-only first phase, exact `localhost` SAN/host on an individually issued lab certificate suffices: explicitly trust the lab CA in disposable hub OS and its isolated Chromium store and use `https://localhost:5445`. This is not a customer private-CA requirement or remote-phone bootstrap. Alternatively use a configured lab DNS name and correctly matched SAN; physical localhost access additionally needs its SAN, or validated configured-host loopback routing. No certificate/trust is created now.
8. **Fresh satellite display:** inspect/apply `scripts/install-satellite.sh` with synthetic hub origin/GUID and actual desktop user. GUID is not cryptographic trust. Verify ordinary display pairing/encounter operation before replacing the launcher; keep the lab Chromium profile for the after comparison.
9. **Full agent installation approval:** the satellite installer alone is insufficient. Install native NM/shared-AP prerequisites, dedicated no-login `initiativetracker-satellite` account, reviewed ARM64 publish under versioned `/opt/initiativetracker-satellite/` and `current` symlink. Install root broker/kiosk from `pi-satellite/` to `/usr/local/libexec/initiativetracker/`, supplied systemd units and `/etc/tmpfiles.d/initiativetracker-satellite.conf`, plus root:agent 0640 `/etc/initiativetracker-satellite/agent.env`.
10. Apply tmpfiles, verify ownership/units, enable `initiativetracker-satellite-network.socket` and independent `initiativetracker-satellite-recovery.timer` before `initiativetracker-satellite.service`. Agent state is agent-owned 0700 `/var/lib/initiativetracker-satellite`; root network state is root-owned 0700 `/var/lib/initiativetracker-satellite-network`; socket is agent-owned 0600. Do not widen privilege or add sudo rules.
11. Back up actual desktop Labwc autostart. Replace only its old satellite launcher with the root-owned N8 kiosk launcher backgrounded; never run competing launchers. Keep `~/.local/share/initiativetracker-satellite/chromium`; do not run Chromium as root.
12. Export the synthetic owner recovery bundle securely during commissioning without logging it or exporting private keys. Initial core trials can omit phone certificate/AP provisioning. Enroll the agent through physical non-secret satellite setup using the exact physical hub TLS pin, then approve its full certificate at the hub's secure physical DM page. Separately approve/link the existing display. Recovery profile provisioning occurs over pinned authenticated TLS, not HTTP. Snapshot both paired lab cards while quiesced and powered off.

Sources: `scripts/installation/install.py`, `pi-network/systemd/`, `pi-satellite/systemd/`, and [installation details](N8-installation-and-validation.md). All apply commands require serial, artifact-hash and fresh-card guards; a complete command appendix follows approval of this checkpoint.

## Rollback and exit

1. Restore isolated router availability/time, let armed root recovery settle and use the approved lab console if needed. Do not disable recovery or delete journals while pending.
2. Retain redacted results/private failure evidence. Shut down and verify power-off before card handling.
3. Existing-Pi option: remove only labelled lab cards, reconnect only approved original boot media/peripherals and reinstall original labelled production cards. Verify expected production root device, healthy unchanged 0.1.5, original encounter/pairing and kiosk. If hardware/firmware changed unexpectedly, stop: a card swap cannot undo it. Use approved original full images only as a separately controlled restoration, never lab identity.
4. Spare-Pi option: restore/discard only lab images. For repetition, restore matching hub/satellite paired snapshots together after binding changes. Full-image restoration is preferred: app/schema/data/keys, agent/root journals, NM profiles, units/config, accounts and desktop profile belong together. Binary-only downgrade is not rollback. Partial installer failure has no automatic uninstall; restore the fresh lab image rather than reinstalling over partial state.
5. Remove only recorded lab root trust from named test stores, or discard isolated lab images/profiles. Dispose only synthetic secrets/CA keys under approved retention; keep production images private. No blanket trust deletion, package removal or user deletion.
6. Report final SHA/artifact hashes, device/card identities, approvals, non-secret state/timing and each case pass/fail/blocked. Never share raw keys, owner/AP files, NM keyfiles, protected journals, cookies, HAR or QR/setup screenshots.

Phase 1 is ready for **procedure/installation approval**, not declared hardware-passed. Require C1–C7 and applicable failure cases, all failures investigated, matching restoration verified and no unexplained identity/network changes. Missing trusted browser bootstrap blocks fresh administration even though agent mTLS itself needs no domain. Present results and exact production proposal separately; do not merge, deploy or modify a working Pi without approval.
