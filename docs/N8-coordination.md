# N8 device coordination and threat model

Status: opt-in prototype implementation; no hardware validation or deployment. See [installation and validation](N8-installation-and-validation.md) for exact infrastructure gates and acceptance requirements.

## Trust and transport

The existing display cookie remains encounter/display authorization only. Network agents enroll separately with a client certificate. A dedicated optional HTTPS listener uses TLS 1.2/1.3; agents pin its complete SHA-256 certificate fingerprint obtained from the physical hub screen. Discovery is an address hint only. Enrollment is approved at the hub DM screen after matching the full client certificate fingerprint shown on the physical satellite. No trust on first use, password envelope cipher, remote reset, or plaintext transport fallback is used. Unknown certificates may reach enrollment but cannot read plans. Every plan/status/action rechecks current enrollment. The HTTPS listener exposes only the coordination API, never browser pages or cookies.

N8-enabled DM PIN authentication and Wi-Fi secret entry require configured trusted browser HTTPS, including on loopback; middleware rejects disallowed submissions before Razor model binding. Fresh PIN authentication uses a separate Secure/HttpOnly DM cookie. All N8 control additionally requires the independent short-lived physical-code grant bound to that fresh login and game session. A legacy gameplay cookie cannot enter network administration, even over HTTPS; physical agent approval still needs exact certificate comparison at the physical hub. N8-disabled legacy compatibility remains explicitly unencrypted. Setup login/network QR links use the validated configured browser origin or stay absent; player/display invitations retain their existing URLs. No global HTTPS redirect or new hostname-wide HSTS is introduced. See [authentication migration and the core hardware checkpoint](N8-authentication-and-core-hardware-trial.md) for compatibility, cookie boundaries and approved lab-only trust without a purchased domain. Production browser/phone infrastructure remains unconfigured. No trust is claimed for legacy public hub GUID discovery or the legacy HTTP display channel.

## Transition contract

Protocol version 1 advertises network.prepare, network.commit, network.recover and network.reconnect capabilities for satellite displays and future wireless bases. Every owner-authorized reassignment creates a new durable intent and generation requiring fresh destination DM approval, including returning to a former hub. Exact retries retain their intent, retired intents are rejected and approval forms bind the visible intent. Enrollment has a generation ID; revocation removes trust and all outstanding authorization. A persistent monotonic revision and UUID identify each transition. Prepare has a fixed expiry; commit persists one fixed activation time and recovery deadline before notification. No DM cancel exists after commit. Offline/unready device names are shown; commit requires explicit IDs to be left behind. A device's successful target reconnection is distinct from the DM's hub confirmation. Both are required to finalize that device.

The hub keeps its existing independent root recovery controllers and timers. Root scheduled switching calls those controllers with the remaining bounded recovery interval. Device recovery is independent of the hub and web process. Satellite intent is written and fsynced before readiness/commit acknowledgments and before network effects. Repeated or stale messages cannot change the deadline. Restart resumes persisted intent. Corrupt journals fail closed rather than guessing a network; repairing corrupted protected storage requires administrator recovery.

Reassignment uses a separate durable binding intent. Candidate authorization cannot exceed the original setup AP lease; expiry is rechecked before and after authenticated hub calls and by the root broker after blocking NM operations. Before root mutation the agent stores the verified destination binding, recovery profile and exact intent in its protected journal. Root atomically records the new generation and committed-intent receipt before scheduling old-profile cleanup. If a reply or subsequent agent save is lost, restart reconciles that exact committed receipt without contacting the hub, even after the former approval deadline. Expired uncommitted intents are aborted; cancellation cannot undo a committed binding. Explicit owner forget is journaled before root reset and takes precedence over pending reassignment. Cleanup persists per-profile progress and treats an already absent profile as a successful retry. Install matching agent and broker versions together; their private IPC contract changed.

## OS and ownership boundaries

The .NET satellite runs as an unprivileged service account. A small root Python broker accepts only bounded JSON operations on a peer-credential checked Unix socket: stage WPA profiles, inspect the active UUID, activate an owned profile, and forget owned profiles. No shell, arbitrary process, password argv or caller-selected path is accepted. A separate independent timer executes durable rollback even while the agent is stopped. Private state files/directories use 0600/0700 and atomic replacement with file and directory fsync. Local recovery uses loopback controls and an optional publicly trusted HTTPS phone endpoint with a unique secured AP, separate owner proof, one-time screen codes, random CSRF tokens, strict Host/Origin checks, bounded sessions and fixed AP leases; remote outages never authorize reassignment. Existing browser pairing and encounter synchronization remain separate.

## Recovery policy

Reachability means an authenticated pinned TLS request, not DNS, ping, SSID or a matching public GUID. Short failures preserve the current profile. At least 120 seconds of consecutive failed probes and at least six failed probes are required before an automatic recovery attempt. Attempts have cooldown/backoff, alternate the known current profile and paired private hotspot, verify the pinned identity after joining, and restore the previous network on failure. A pending coordinated transition takes precedence over ordinary recovery. The root timer deliberately reactivates the last identity-verified finalized profile after boot and requires the agent to reverify the pinned hub before finalizing that boot trial. The radio has one active transition or provisioning lease; failed lease restoration retains durable retry intent and cannot interrupt an armed transition. The lease owns a unique candidate UUID; its expiry disconnects unapproved candidates as well as the setup AP, and an interrupted teardown remains retryable. Closing the bounded AP window resets recovery-cycle escalation so the agent resumes preferred-network and private-hotspot trials. A local touch recovery action remains available when the old hub is unreachable.
