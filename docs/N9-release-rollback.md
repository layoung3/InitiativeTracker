Automatic updater restoration of stale secure grants must be corrected by the shared task before combined release acceptance.

Status: N9 software candidate **0.1.6**, **not approved for publication, merge or installation**. N8 PR #4 remains separate, draft and unmerged at `93e93d37ffa5dfdc809434751f6b641087d7913c`. N9 starts from master `d584b7963ca6bb7916f21d9ee94082f9f2821f34`; it does not include N8 TLS/network-agent changes.

**Deployment dependency:** an existing HTTP-only 0.1.5 installation cannot use custom private media or image/branding-settings changes until trusted HTTPS is separately approved and configured for its application/authentication origin. Production returns 426 for these HTTP requests; do not bypass certificate trust, enable Development on a Pi, or import unmerged N8 infrastructure to work around this requirement. Neutral image defaults, public product branding/loading and existing gameplay remain available. This software candidate is not a deployment-ready commissioning claim.

## Presentation configuration

`Branding:ApplicationName` accepts a trimmed name of at most 80 characters, rejects control characters and falls back to `Initiative Tracker`. Razor encodes the name as ordinary text. `Branding:ShowApplicationLogo` controls optional branding on application entry pages; Setup and waiting screens retain product branding. No setting accepts HTML, CSS, a filesystem path or a remote image URL. The Colophon artwork is independent of the default neutral adventurer portrait and mountain banner.

The original supplied raster is retained unchanged at `InitiativeTracker.Web/wwwroot/images/colophon.png`, verified as 73,110 bytes / 300×300 with SHA256 `17822fd1b2b7f54f3b084ce19b24d51f50f30e0495529ba8679586145def40b1`. DM can replace the application logo through **Branding & banners** using the same validated PNG/JPEG pipeline, without changing source. A replacement lives in private persistent storage and is intentionally served publicly from `/branding/logo`. Removing it restores the supplied Colophon original. Runtime DM name/visibility settings override the optional configuration defaults.

## Before a release can be approved

- Review the implemented image pipeline, ownership/visibility rules, cleanup and failure tests, plus the approved SkiaSharp 4.154.0 dependency audit. Confirm independent review findings are resolved.
- Inspect real artwork and actual rendered pages at phone, tablet/landscape and desktop/display sizes. Record software checks and physical observations separately.
- Run .NET Release tests, Chromium suites, network/installer/updater tests, shell checks, self-contained ARM64 publish and existing Build/Test release-manifest tools on the final source head. Confirm any native decoder and licenses are included. Record exact-head GitHub CI, not an earlier success.
- Review runtime changes separately from the application archive. App releases do not silently replace the desktop launcher/supervisor or alter OS boot configuration. Confirm current updater health, backup and rollback behavior in disposable fixtures.
- Candidate source version is 0.1.6, distinct from the working 0.1.5 installation. Do not overwrite old archives or immutable release directories. No release tag/publication or deployment is authorized by this guide.

## Later approved installation

No step here is to run on the owner's current cards now. No spare cards are presently available. Later validation can use the existing two Pis with separate disposable microSD cards, a reader and private image/backup storage; two additional Pis are unnecessary. Shut down, remove power fully, label/store original cards and verify boot-media isolation before using disposable installations. Restore original cards and boot-media arrangement only while fully powered off; then verify unchanged 0.1.5 health, pairing and encounters. Do not alter EEPROM or attached production storage.

For a later approved application update, first configure trusted HTTPS for the authentication/application origin and verify browser trust without bypasses. Production private-image reads and image/settings writes require HTTPS; Development is for disposable fixtures only. Configure `Tracker:DataDirectory` explicitly outside the application/versioned release directory (the usual `/var/lib/initiativetracker` layout); production media/settings writes are refused when persistence is not configured safely. Then use the existing versioned release archive/manifest and graphical updater. Keep `Tracker:DataDirectory`, data-protection keys, player/device identity and browser profiles intact. Back up the **entire data directory**, not only SQLite. New uploaded media must live under that directory and outside `wwwroot`, so database and media restore together. A live database/file copy is not a verified backup.

N9 includes additive EF migration **`20261031050702_AddPresentationAssets`**, creating **`PresentationAssets`** and **`PresentationSettings`**. `Program.cs` automatically calls `db.Database.Migrate()` during application startup, before serving requests. Consequently, the first N9 start against an existing data directory is a live database migration and requires separate explicit approval as part of a future deployment. No live migration has been performed here; tests use disposable databases. Stop the application and preserve a verified, matching database/private-media/key backup before that approved first start.

For a later separately approved desktop-component update, preserve the chosen user's actual passwd home. The launcher is under `~/.local/lib/initiativetracker-hub/initiativetracker-hub-launch`, not `/usr/local/bin`. Back up exact launcher/supervisor/waiting artwork and metadata before a reviewed replacement. The existing component utility recognizes exact hashes; if it refuses an installed version, stop and review rather than widening hash acceptance or overwriting it. New N9 candidate hashes do not themselves authorize a component update.

The fresh installer copies the waiting page and verified Colophon image to the selected role's home-local directory. Existing installations require a separately reviewed copy/restore plan for these files; an app archive does not install them. Preserve current Labwc autostart, LightDM, display mode, Chromium profile paths and graphical checker. Hub ordering remains health → checker/update → health → Chromium. A startup dialog is closed before the checker and before Chromium, including failure and signal exits. The satellite's local waiting browser uses an independent profile and is terminated before the persistent paired display is opened. No certificate bypass or HTTP fallback is added.

For future customer branding on desktop-local startup screens, a separately approved desktop asset refresh can use the normalized public `/branding/logo` PNG as the fixed home-local `colophon.png` asset, keeping the original bundled Colophon raster intact. Back up and hash the prior local asset first, validate the downloaded PNG through the approved decoder, and install it for the selected desktop owner at the documented fixed path. Do not introduce arbitrary URL/path configuration or refresh from an unverified origin. Application branding changes refresh live pages; local startup caches require this separate reviewed copy. Neither path requires source edits.

## Rollback

Before an approved application update, preserve the old release link and private whole-data backup with matching version/manifest evidence. Let the graphical updater perform its existing health-gated rollback; check its result rather than assuming every failure proves recovery. If automatic recovery fails, stop and inspect locally before moving data or invoking another update. Restore database and media from the same backup, retain failed state for diagnosis, and verify session/identity/pairing/encounters after recovery.

For downgrade, restore the prior application release and its matching whole-data backup together while the application is stopped. Preserve the failed/new data separately for diagnosis; verify private media, database, identities and keys after restoration. The migration's `Down` operation **drops both presentation tables**: never casually run `Down`, remove table rows or delete asset files as a rollback shortcut. An application-link change alone is not a full data downgrade.

Desktop components/artwork have a separate backup and rollback; restoring an app link alone cannot restore them. Restore only the exact backed-up files and permissions after checking for later user changes. Restart the desktop only with explicit approval. OS splash experiments have a separate [optional investigation and recovery plan](N9-optional-boot-splash.md); card swaps cannot undo firmware changes.
